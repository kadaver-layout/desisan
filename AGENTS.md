# Правила работы с DESISAN

Эти инструкции действуют для всего проекта. Перед началом работы прочитать этот
файл и проверить инструкции во вложенных AGENTS.md. Сохранять правила при дальнейшей работе.

## Требования пользователя

- Соблюдать комментарии для верстальщика на каждой странице Figma.
- Изучать лист библиотеки Figma: описания поведения, состояния компонентов,
  варианты и правила использования обязательны для реализации.
- Перед установкой любой новой библиотеки сначала сообщить пользователю название,
  задачу и причину выбора; дождаться явного согласия. Это относится и к devDependencies.
  Не изменять зависимости и lock-файл для добавления пакетов без согласования.
- Вёрстка должна быть пригодна для интеграции в Битрикс.
- JavaScript должен быть понятным, читаемым, с комментариями.
- Соблюдать семантику HTML, правила контейнеров и адаптивность.
- Структура страниц и организация исходников — как в предыдущем union-layout.
- Логику сборки сохранять идентичной union-layout; изменения согласовывать.

## Источник дизайна

Figma: https://www.figma.com/design/KPYwWJy0qNwCsycikeMwUH/DESISAN?node-id=0-1

Перед вёрсткой конкретной страницы:

1. Прочитать относящиеся к ней комментарии и аннотации для верстальщика.
2. Изучить соответствующие компоненты и правила на листе библиотеки.
3. Проверить все доступные разрешения, состояния и поведение элементов.
4. Получить контекст дизайна и скриншоты через инструменты Figma с соблюдением
   навыка figma-design-to-code. Если описание неполное, запросить нужные дочерние узлы.
5. При недоступности комментариев или листа библиотеки сообщить об этом:
   не считать их прочитанными, не выдумывать требования. Если от них зависит
   реализация, запросить недостающую информацию до зависимых изменений.

Стартовая страница и её базовые значения не являются готовой реализацией макета.
Текущие шрифты, цвета, контейнер и брейкпоинты уточнять по Figma.

## Структура проекта

```text
desisan/
  AGENTS.md
  README.md
  package.json
  package-lock.json
  gulpfile.js
  projectConfig.json
  .gitignore
  src/
    index.html                  # стартовая страница
    *.html                      # отдельный файл каждой следующей страницы
    html/
      layouts/
        default.html            # общий документ, head, шапка, подвал, модалки
      includes/
        header.html
        footer.html
        modal.html
        *.html                  # переиспользуемые блоки
    data/
      data.json                 # общий контекст Nunjucks
    assets/
      styles/
        main.sass               # точка входа, подключения через @use
        _vars.sass              # общие переменные и брейкпоинты
        style.sass              # базовые стили и контейнеры
        index.sass
        header.sass
        footer.sass
        modal.sass
        *.sass                  # стили отдельных блоков
        libs/
          splide.min.css        # отдельно собираемые стили библиотек
      js/
        app.js                  # основной JS, инициализация компонентов
        *.js                    # дополнительные модули при необходимости
      img/                      # локальные изображения и иконки
      fonts/                    # локальные шрифты
      video/                    # видео
      libs/                     # резерв; отдельной задачи копирования нет
  node_modules/                 # зависимости, не редактировать
  dist/                         # генерируемая сборка, не редактировать вручную
    *.html
    html/                       # копии исходных шаблонов
    assets/
      css/main.css
      css/libs/
      js/app.js
      js/raw/                   # копии исходного JS, не подключать к странице
      img/
      fonts/
      video/
```

Пустые папки ресурсов сохраняются через .gitkeep. Новые блоки и страницы
добавлять в соответствующие существующие папки, без альтернативной структуры.

## HTML и подготовка к Битрикс

- Использовать Nunjucks: страницы расширяют layouts/default.html через extends,
  основной контент располагается в block content. title и meta_description задавать для страницы.
- Общие шапка, подвал и модалки подключаются из includes в layout.
  Не дублировать их вручную в каждой странице.
- Повторяющиеся блоки выносить в includes, повторяющийся контент — в data.json
  с выводом через циклы Nunjucks, как в union-layout.
- Собирать готовый HTML на этапе Gulp, не генерировать основной контент страницы
  в браузере из JSON. Разметка должна переноситься в шаблоны и компоненты Битрикс.
- Не привязывать компоненты к точному числу карточек или длине демонстрационного текста.
  Учитывать длинные названия, отсутствие изображения и пустые списки, когда они предусмотрены.
- Разделять динамические данные и разметку; имена классов и data-атрибутов делать
  предсказуемыми для интегратора. Не выдумывать серверные URL и обработчики Битрикс.
- Не подключать общий CSS/JS повторно внутри компонента, не вкладывать страницы
  с собственным head/body в шаблон компонента.
- Один main и осмысленный h1 страницы, последовательная иерархия заголовков.
  nav — для навигации, списки — для перечней, article — для самостоятельных карточек.
  Ссылки — для переходов, button — для действий, type у кнопок указывать явно.
- Поля форм связывать с label, использовать корректные типы и name.
  Значимые изображения снабжать alt, декоративные — пустым alt.
- Интерактивные компоненты должны работать с клавиатуры и иметь видимый фокус;
  aria-expanded, aria-controls и другие состояния обновлять вместе с интерфейсом.

## Sass, контейнеры и адаптация

- Использовать существующий Sass с отступами и БЭМ: block__element, модификаторы
  по принятой в проекте схеме. Не вводить Tailwind, CSS-in-JS и другой стек.
- Стили блока хранить в отдельном .sass и подключать через main.sass.
  Общие переменные подключать через @use "_vars" as *.
- Цвета, шрифты и повторяющиеся параметры централизовать; ориентироваться на
  токены и библиотеку DESISAN. Не переносить оформление СОЮЗ в новый дизайн.
- Ограниченную ширину, горизонтальные поля и центрирование задавать контейнером.
  Полноширинный фон принадлежит секции; содержимое ограничивается контейнером,
  если именно так задано макетом. Не удваивать отступы вложенными контейнерами.
- Согласовывать контейнеры шапки, основного контента и подвала по макету.
  Различающиеся по макету типы контейнеров оформлять явными классами.
- Использовать Grid/Flex и нормальный поток. Не копировать координаты Figma
  абсолютным позиционированием для обычной структуры страницы.
- Адаптацию строить по макетам и поведению компонентов; проверять промежуточные
  ширины, переносы текста, порядок элементов, размеры изображений и отсутствие overflow.
- Использовать локальные ассеты макета; временные ссылки Figma не оставлять в коде.

## JavaScript и библиотеки

- Использовать ES-модули и существующую сборку Webpack, основной вход — app.js.
- Инициализировать компоненты после готовности DOM и только при наличии их элементов.
  Несколько экземпляров одного блока на странице должны работать независимо.
- Давать функциям и переменным понятные имена. Комментарии писать по-русски:
  назначение блока, нетривиальное поведение, причины решений и точки интеграции.
  Не оставлять отладочные console.log, мёртвый код и непрозрачные цепочки действий.
- Предпочитать data-атрибуты для JS-хуков. Не смешивать данные, DOM и сетевую
  логику в одном большом обработчике. Не дублировать обработчики при повторной инициализации.
- Соблюдать поведение и состояния из библиотеки Figma, включая открытие/закрытие,
  валидацию, фокус, ошибки и мобильные варианты, если они предусмотрены.
- Не имитировать успешную серверную отправку, покупку или авторизацию.
  Если серверной части нет, явно фиксировать точку подключения для разработчика.
- Уже установлены Tom Select, Splide, Splide Grid, MicroModal, jQuery.
  Наличие пакета не означает необходимость его использовать. Перед новой
  библиотекой обязательно согласование пользователя; существующие использовать по задаче.
- JS библиотек подключать npm-импортами, а не случайными CDN-скриптами.

## Сборка: сохранять существующее поведение

- Node.js 22.13+; точные версии пакетов — в package-lock.json, установка npm ci.
- npm run dev: Gulp build, затем watch и BrowserSync из dist.
- npm run prod: то же с --prod; это не разовая сборка, сервер и watch остаются.
- npx gulp build: разовая development-сборка.
- npx gulp build --prod: разовая production-сборка.
- Полная сборка очищает dist, затем параллельно выполняет html, htmlRaw, scss,
  js, jsRaw, image, video, fonts.
- Nunjucks читает src/data/data.json и шаблоны из src/html.
- main.sass собирается в dist/assets/css/main.css, styles/libs — в css/libs.
- Development: source maps для CSS и JS. Production: Autoprefixer (grid: true),
  сортировка media queries, JS через Terser без mangle/compress, с beautify.
  CSS не минифицируется; не менять это поведение самовольно.
- Webpack собирает app.js, оригинальные модули копируются в assets/js/raw.
- Изображения копируются, JPG/JPEG/PNG/GIF конвертируются Sharp в WebP (quality: 80).
  Шрифты WOFF/WOFF2/TTF и видео MP4 копируются отдельными задачами.
- projectConfig.json сохранён из шаблона, но Gulp использует пути из gulpfile.js.
- assets/libs не копируется задачей Gulp; libsJs пока пустой.
- В правиле Webpack есть .ts, но TypeScript и ts-loader не установлены:
  использовать JS; добавление инструментов сначала согласовать.
- Watch отслеживает JSON/JS в data, но контекст берётся только из data.json.

## Проверка перед завершением задачи

- Сверить результат с макетом, комментариями страницы и правилами библиотеки.
- Собрать проект, убедиться в отсутствии ошибок сборки.
- Проверить изменённые страницы в браузере на всех соответствующих размерах
  макета и промежуточных ширинах, включая минимальную мобильную.
- Проверить отсутствие горизонтального скролла, обрезанного текста, перекрытий,
  сломанных изображений и ошибок JS. Не скрывать ошибки overflow-x: hidden.
- Проверить сценарии изменённых компонентов, клавиатуру и состояния форм.
- Для изменений сборки проверить development и production, выходные файлы,
  source maps и копии исходников. Не считать одну успешную команду достаточным
  доказательством визуального совпадения или работоспособности интерфейса.
- В сообщении пользователю кратко указать результат, проверку и оставшиеся
  ограничения. Не называть стартовую структуру готовой вёрсткой.
